---
title: Branching model
description: Why the template ships the dev integration flow switched on, and why main-only is a documented edit rather than a variant.
icon: lucide:git-branch
---

The template runs a `dev` integration branch: work lands on `dev`, a rolling
promotion PR carries it into `main`, and release-please releases from `main`.

## Why `dev` is the default

It is what most kirchDev repos run. A variant that ships switched off is a
variant nobody notices is broken, so the common flow is the one the template
exercises every day.

The cost of that choice is one trap: a repo created from the template has the
`dev` configuration but **no `dev` branch**, and Dependabot pointed at a branch
that does not exist opens nothing at all — silently. Going main-only is a
deliberate step for the same reason: leaving the configuration untouched is the
one option that fails without a signal.

## Why the promotion PR is never squashed

release-please reads the commits that land on `main`. A squash collapses the
individual `feat:` and `fix:` commits into the promotion PR's own `chore:`
title, and release-please then cuts nothing. A merge commit keeps them.

The promotion body picks its own target — `stage` when that branch exists,
otherwise `main` — so the stub in `.github/workflows/promotion-pr.yml` is the
same file whichever flow a repo runs.

## Why main-only is documented, not vendored

A variant worth shipping as files is one that **adds** something that would
otherwise be lost. Main-only only removes — a workflow, two Dependabot lines, a
config value — so there is nothing to preserve, and the edit stays a short list
in `AGENTS.md`.

The CI and CodeQL branch filters keep `dev` even then. A filter naming a branch
that does not exist is a no-op and costs a main-only repo nothing; dropping it
from a repo that does run `dev` would leave its pull requests, Dependabot's
included, with no CI at all.
