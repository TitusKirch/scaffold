title: Permission policy
description: Why the agent permission files block generously, allow sparingly, and leave everything else to a prompt.

---

`.claude/settings.json` and `.codex/rules/default.rules` are deliberately
lopsided: a long `deny` list and a short `allow` list. The two sides answer
different questions, so they follow opposite rules.

## Three states, not two

A command in `allow` runs unasked; one in `deny` is impossible and has to be
typed by hand; one in neither list **prompts**. That middle state is the right
default for almost everything. `deny` is reserved for what a mistaken "yes"
could not undo, and a command that is sometimes wanted belongs in the middle,
never in `deny`.

## Why `deny` may be generous

A rule for a command the repo does not have is a no-op: it never needs
maintenance and nobody has to review it, and a block that is too broad only
surfaces when someone actually hits it. So the list covers every stack a
kirchDev repo might grow into — Laravel, Prisma, Terraform/OpenTofu, AWS — not
just this one, and a downstream repo keeps it as-is.

The line it draws is **the machine or something remote, not the working copy**:
wrecking the OS, tearing down remote state, or throwing away work with no
recovery path. `git reflog expire` and `git gc --prune=now` sit there for that
last reason — they destroy the rescue path that survives a `reset --hard`.
`rm -rf node_modules`, `docker compose down -v` or deleting a remote branch are
ordinary local development, so they prompt instead.

## Why `allow` must stay short

Its only return is fewer prompts; no safety is gained. Every line has to be read
and understood by whoever copies the file, and an unreviewed allow list is more
dangerous than none. What earns a line is what occurs many times per session.
A plain `git push` does: it is reversible, visible and the ordinary way work
ships — force-pushing is the part that is denied.

A single allow rule that runs arbitrary code hands back everything `deny` took
away: a blocked `db:wipe` means nothing next to an allowed
`tinker --execute 'DB::statement(...)'`. A deny list is only as strong as the
weakest allow rule beside it.

## What the files cannot do

Neither file can tell which branch a push targets, so release branches are
protected by branch protection, not permissions. Prefix rules also miss flags
placed before the subcommand. The policy lowers the odds of a destructive
mistake; it is not a guarantee.

## Why there are two files

Permission config is not portable between agents, so the block list exists
twice. Codex matches whole argv tokens, which catches flags and shell chains the
Claude Code string prefixes miss — and the cost is that the two must change
together. `pnpm check:policy` turns "we changed both files" into a number rather
than a claim. Where the two rule languages force a difference, and why the
check proves the same spellings rather than completeness, is stated in the
header of `.codex/rules/default.rules`.
